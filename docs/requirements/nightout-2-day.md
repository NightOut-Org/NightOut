# แท็บ: NightOut — Requirement

## NightOut.day — Requirement (Revised Business Requirement Document & Scope Statement)
#### 
#### 1. ภาพรวมโครงการและวัตถุประสงค์เชิงกลยุทธ์ (Project Overview & Strategic Objectives): NightOut.day

1.1 รายละเอียดแพลตฟอร์ม (Platform Description):
Nightout.day คือ แพลตฟอร์มศูนย์รวมข้อมูล การค้นหา และการวางแผนเที่ยวกลางคืนแบบครบวงจร (One-Stop Nightlife Ecosystem) ที่มุ่งแก้ไขปัญหา (Pain Points) ของทั้งฝั่งผู้บริโภค (Nightlife Goers) และผู้ประกอบการร้านค้า (Merchant Partners) โดยประยุกต์ใช้เทคโนโลยีเพื่อยกระดับประสบการณ์การค้นหาร้าน การจองโต๊ะ การชำระเงิน ดูความปลอดภัย คอมมูนิตี้ การตั้งกระทู้รวมทั้งหาเพื่อนเที่ยว และการบริหารจัดการลูกค้าระหว่างช่วงเวลาให้บริการ
1.2 โครงสร้างระบบหลัก (System Components):
แพลตฟอร์มประกอบด้วย 3 ส่วนหลัก ที่เชื่อมโยง Flow การทำงานอย่างโปร่งใสตั้งแต่ การจองโต๊ะ -> จ่ายมัดจำ -> สแกนเข้าร้าน -> ไปจนถึงการเคลียร์เงิน/คืนเงิน ได้แก่:

- Customer App (Mobile Application สำหรับลูกค้า)
- Merchant Dashboard (Web/Tablet Application สำหรับร้านค้า)
- Admin & Super Admin Panel (Web Application สำหรับทีม Operation และผู้บริหาร)
1.3 ชื่อโครงการและเป้าหมายเชิงระยะเวลา (Project Name & Phasing):
Nightout Platform Development

- Phase 1: Market Validation (พิสูจน์ตลาดด้วยระบบ Manual)
- Phase 2: Monetization (เชื่อมต่อ Payment Gateway และระบบหัก GP 5–7%)
1.4 วัตถุประสงค์โครงการและตัวชี้วัดความสำเร็จ (Project Objectives & Measurable KPIs):

- วัตถุประสงค์หลัก (Primary Objectives): บริหารจัดการการจองโต๊ะและรับเงินมัดจำ เพื่อแก้ไขปัญหา No-show ให้กับผู้ประกอบการ และช่วยผู้บริโภคควบคุมงบประมาณได้อย่างแม่นยำ
- วัตถุประสงค์รอง (Secondary Objectives): สร้างพฤติกรรมการชำระเงินล่วงหน้า (Pre-paid), นำร่องลิงก์หารค่าใช้จ่ายให้กลุ่มเพื่อน (ผู้จองจ่ายคนเดียว) และจัดเก็บข้อมูลพฤติกรรมผู้ใช้เพื่อขยายระบบในอนาคต
- ตัวชี้วัดความสำเร็จ Phase 1 (Phase 1 KPIs - Soft Launch): Active Merchants 5–10 ร้าน, MAU 10,000 คน, อัตรา No-show < 5%, สัดส่วนการใช้ลิงก์หารเงิน > 50% ของรายการจองทั้งหมด
- ตัวชี้วัดความสำเร็จ Phase 2 (Phase 2 KPIs - Monetization): MAU 25,000+ คน, อัตราการจ่ายเงินผ่าน API สำเร็จ > 95%, รายได้จาก GP เติบโตอย่างน้อย 20% MoM, สัดส่วนการเลือก Fast-Track > 15%
- ตัวชี้วัดความสำเร็จ Phase 3 (Phase 3 KPIs - Retention & Ads): อัตราการกลับมาใช้ซ้ำ (User Retention Rate) > 30%, รายได้จากโฆษณา (Ad Revenue) คิดเป็น > 15% ของรายได้รวมทั้งหมด
- ผลงานส่งมอบที่สำคัญ (Key Deliverables): แอปพลิเคชันฝั่งลูกค้า (Customer App), เว็บ/แท็บเล็ตแดชบอร์ดฝั่งร้านค้า (Merchant Dashboard), ระบบควบคุมฝั่งแอดมิน (Admin Panel) พร้อมเอกสารสถาปัตยกรรมระบบ (Database Schema, API Specs, Flowcharts, RBAC Matrix)
1.5 ปัญหาที่โครงการต้องการแก้ไข (Problem Statement):

- ฝั่งลูกค้า (Customer Pain Points):
- มีข้อจำกัดด้านงบประมาณ (เฉลี่ย 200–500 บาท/คน) และขาดเครื่องมือค้นหาร้านตามงบประมาณจริงแบบ Real-time ทำให้ควบคุมงบได้ยาก
- การบริหารจัดการกลุ่มเพื่อนทำได้ยาก (เช่น เพื่อนมาสาย, โต๊ะหลุด, ไปถึงร้านแล้วไม่มีโต๊ะรองรับ)
- ความวุ่นวายในการหารค่าใช้จ่าย ต้องมีบุคคลสำรองจ่าย และมีความเสี่ยงต่องบบานปลาย
- ต้องยืนรอคิวหน้าร้านเป็นเวลานาน และขาดระบบรีวิว/จัดอันดับที่เป็นกลางเพื่อประกอบการตัดสินใจ
- ฝั่งร้านค้า (Merchant Pain Points):
- อัตราการจองแล้วไม่มา (No-show) สูง ส่งผลให้สูญเสียรายได้และเสียโอกาสจากโต๊ะว่าง
- ความวุ่นวายในการจัดการคิวหน้าร้านช่วง Peak Hour, การจัดการพนักงานรับออเดอร์/เช็คบิลไม่ทัน และปัญหายอดขายต่ำในวันธรรมดา
- ฝั่งแอดมินระบบ (Admin Pain Points):
- ขาดเครื่องมือคัดกรองมาตรฐานร้านค้า, การตรวจสอบความปลอดภัย (Safety Verification) และระบบจัดการข้อพิพาทอย่างเป็นระบบ
1.6 กลุ่มเป้าหมายและผู้มีส่วนได้ส่วนเสีย (Target Audience & Stakeholders):

- กลุ่มผู้ใช้งาน (Customers):
- กลุ่มเป้าหมายหลัก (Primary Target - "The Party Gang"): นักศึกษา และ First Jobber อายุ 20–25 ปี เดินทางเป็นกลุ่ม 2–8 คน (งบประมาณ 200–350 บาท/คน) โดยมีแกนนำ 1 คนเป็นผู้ทำรายการจอง (เน้นการคุมงบ)
- กลุ่มเป้าหมายรอง (Secondary Target): First Jobber เดินทางเป็นกลุ่ม 2–4 คน (งบประมาณ 400–1,000+ บาท/คน) นิยมเที่ยววันศุกร์–เสาร์ และยินดีจ่ายเพิ่มเพื่อแลกกับสิทธิพิเศษ (เช่น Fast-Track)
- กลุ่มผู้ประกอบการ (Merchant Stakeholders): ร้านค้ารายย่อย และพนักงานต้อนรับหน้าร้าน (Reception)
- กลุ่มผู้บริหารระบบ (Admin Stakeholders): ทีม Operation และฝ่าย Support ของ NightOut (รวมถึงผู้บริหารระดับ Super Admin)
1.7 พื้นที่ดำเนินการนำร่อง (Launch Location & Rollout Strategy):

- จุดเริ่มต้น: 1 โซนนำร่อง บริเวณรอบมหาวิทยาลัยหอการค้าไทย
- แผนการขยายผล (Expansion Plan): ขยายไปยังโซนอื่นๆ ตามเครือข่ายพันธมิตร (Strategic Connections ของคุณที) และต่อยอดทราฟฟิกจากกลยุทธ์ Content Marketing ของทีมงาน

1.9 การบริหารจัดการความเสี่ยง (Risk Management & Mitigation Strategies):
- ความเสี่ยงข้อพิพาทเรื่องการยึดมัดจำ/มาสาย: บังคับให้การเช็กอินทำผ่านการสแกน QR Code ที่ผูกกับ Server Timestamp กลาง และกำหนดให้แสดง Refund Policy พร้อมกล่อง Check-box ยืนยันก่อนการชำระเงินทุกครั้ง
- ความเสี่ยงความล่าช้าในการเชื่อมต่อ Payment Gateway: เริ่มเชื่อม Beam Payment ตั้งแต่ต้น Phase 1 (ไม่มีทางสำรองแบบโอน + แนบสลิป)
- ความเสี่ยงด้านข้อกฎหมายควบคุมแอลกอฮอล์: กำหนดการคัดกรองเนื้อหาและตรวจสอบสื่อโปรโมชันทั้งหมด ไม่ให้มีคำว่า "ขายเหล้า/เบียร์" หรือการลดราคาแอลกอฮอล์ พร้อมปรับป้าย Safety เป็น "ข้อมูลจากร้านค้า" พร้อมระบุวันที่ตรวจล่าสุด
- ข้อจำกัดด้านกฎหมาย (Legal Compliance Constraints): ห้ามจำหน่าย/พรีออเดอร์เครื่องดื่มแอลกอฮอล์หรือจัดโปรโมชันลด/แถมแอลกอฮอล์ผ่านแอปพลิเคชันโดยเด็ดขาด ให้ระบุเป็น "ค่าธรรมเนียมจองโต๊ะ (Table Fee)" หรือ "เซ็ตอาหาร/มิกเซอร์" เท่านั้น
- ข้อจำกัดด้านเทคโนโลยีและสถาปัตยกรรม (Technical Constraints): โครงสร้าง Database ใน Phase 1 ต้องออกแบบให้ยืดหยุ่นเพียงพอรองรับการเปลี่ยนผ่านไปสู่ API Automation ใน Phase 2; การปรับเปลี่ยน System Settings และ Database Schema จะทำผ่าน Migration โดยทีม Tech เท่านั้น ไม่เปิดให้ปรับแก้ผ่าน Admin UI
- ข้อสันนิษฐานด้านการดำเนินงาน (Operational Assumptions): สันนิษฐานว่าระบบ Centralized Billing ใน Phase 2 จะเป็นการป้อนยอดรวมผ่าน UI โดยร้านค้า

### 3. กฎที่ใช้ทั้งระบบ
•        ผู้ใช้ต้องยืนยันอายุ 20+ ตอนสมัคร และกดยอมรับ ToS + PDPA Consent ก่อนใช้งาน
•       นิยามเงินมัดจำ (Legal Compliance): ต้องใช้คำว่า "ค่าธรรมเนียมจองโต๊ะ (Table Fee)" เท่านั้น ห้ามมีการทำรายการซื้อขาย/พรีออเดอร์ "แอลกอฮอล์" ผ่านแอปพลิเคชันโดยเด็ดขาด
•      ห้ามขาย/พรีออเดอร์เครื่องดื่มแอลกอฮอล์ผ่านแอป · ห้ามใช้คำว่า "ขายเหล้า/เบียร์" ในแอปและแคมเปญ · 🆕 ระบบขายเครื่องดื่มแอลกอฮอล์โดยตรงอยู่นอกขอบเขตโครงการ
•      โปรโมชันของร้านต้องเป็นของที่ไม่ใช่แอลกอฮอล์เท่านั้น (มิกเซอร์, อาหาร, น้ำแข็ง, ส่วนลดวันเกิด) ห้ามลดราคา/แถมแอลกอฮอล์
•      ทุกการจองจ่ายเฉพาะค่ามัดจำโต๊ะ
•      เงินมัดจำจะถูกชำระผ่าน Payment Gateway (Beam Payment) แบบ Escrow ตั้งแต่ Phase 1 ต่อเนื่อง Phase 2 · ไม่มีการโอน + แนบสลิป 
•      ต้องกดยอมรับ Refund Policy (ข้อตกลงยึดมัดจำ 30 นาที) ผ่านปุ่ม Check-box ก่อนชำระเงินทุกครั้ง
•      แจ้งเตือนลูกค้าก่อนถึงเวลาจอง 15 นาที · หากใกล้หมดเวลา ลูกค้าสามารถกด "ขอต่อเวลา 15 นาที" ได้ 1 ครั้ง · กฎการเช็คอิน: ถือว่าเช็คอินสำเร็จเมื่อ "สมาชิกคนแรก" ของกลุ่มสแกน QR โค้ดสำเร็จ เพื่อป้องกันโต๊ะหลุด · หากมาสายเกินเวลา ระบบจะปลดโต๊ะอัตโนมัติ (Forfeited) และร้านยึดมัดจำ 100%
•      การเช็กอินต้องสแกน QR ผูกกับ Timestamp ของ Server กลางเท่านั้น (กันข้อพิพาท "มาตรงเวลาแต่พนักงานไม่กดเช็กอิน")
•      นโยบายยกเลิก/คืนเงิน: แยกเงื่อนไขก่อน 24 ชม. คืนเต็มจำนวน(กลุ่ม) และ ก่อน 6 ชม.คืนเต็มจำนวน (ทั่วไป) เรท 200-300 บ./คน
•      ร้านไม่มีโต๊ะให้: ให้ติด Blacklist
•      ป้าย Safety ต้องระบุวันที่ตรวจสอบชัดเจน โดยบังคับใช้คำว่า "ข้อมูลอ้างอิงจากร้านค้า (Merchant Declared)" พร้อมวันที่ตรวจล่าสุด และมีข้อความปฏิเสธความรับผิด (Disclaimer) ห้ามใช้คำว่า "Safety Verified" เด็ดขาด เพื่อป้องกันความเสี่ยงทางละเมิด
•      การจ่ายเงินโปรโมท/โฆษณา ไม่มีผลต่อดาวและอันดับ · ร้านที่โปรโมทติดป้าย "แนะนำ · โฆษณา" เสมอ
•      การตั้งค่าโครงสร้าง Database และ System Settings (รวมข้อมูลโครงสร้างเชิงลึก) แก้ผ่าน Migration โดยทีม Tech เท่านั้น ไม่เปิดให้แก้ผ่าน Admin UI / Dashboard
•      การชำระเงิน: ผู้จองจ่ายยอดรวมคนเดียว ไม่แยกจ่ายรายคน (ไม่ทำ Split-Pay)
•      PDPA: ต้องขอความยินยอมก่อนนำข้อมูลการจอง/พฤติกรรมไปใช้ต่อ

### Phase 2: Payment Automation & Monetization
ระยะเวลา: เดือน 4–6
เป้าหมาย: จ่ายเงินอัตโนมัติ 100% ผ่าน Beam Payment (ต่อจาก Phase 1) · เริ่มเก็บค่าคอม (GP) 5–7% · ขยายโซนที่ 2 (ทองหล่อ / เอกมัย / อารีย์) และกลุ่ม First Jobber
🆕 ขอบเขตงาน Phase 2 ตาม Brief: เชื่อม Payment Gateway (Beam Payment) · หัก GP · Fast-Track Entry · ดูบิลรวม (Centralized Billing)
ตัวชี้วัดความสำเร็จ:
•      จ่ายผ่าน API สำเร็จ > 95%
•      เก็บ GP อัตโนมัติครบถ้วน · รายได้ GP โตอย่างน้อย 20% ต่อเดือน
•      สัดส่วน Split-Pay > 50%: ตัดออก เพราะ Phase 2 ให้ผู้จองจ่ายยอดรวมคนเดียว ไม่มีการแยกจ่ายรายคน (ลิงก์หารเงินใน Phase 1 เป็นแค่การแชร์ยอดต่อหัวให้เพื่อนดู เงินยังจ่ายโดยผู้จองคนเดียว) · ตัวชี้วัดที่เสนอใช้แทน: สัดส่วนการจองที่จ่ายผ่าน Payment Gateway สำเร็จ หรือสัดส่วนการจองที่แชร์ลิงก์หารเงิน
•      การจองที่เลือก Fast-Track > 15%

## 5. ปัญหาฝั่งผู้ประกอบการและทางออก (Merchant Pain Points & Solutions)
- อัตราการ No-Show สูง: ลูกค้าจองแล้วไม่มา ทำให้สูญเสียรายได้จากโต๊ะว่าง แก้ไขโดยกำหนดระบบมัดจำและการยึดโต๊ะอัตโนมัติหากเลทเกิน 30 นาที
- ยอดขายต่อหัวต่ำในวันธรรมดา: แก้ไขด้วย Dynamic Deals ปรับเปลี่ยนโปรโมชันตามช่วงเวลาเพื่อกระตุ้น Traffic ในช่วง Off-Peak
- ภาระงานของพนักงานช่วง Peak Hour: ลดขั้นตอนการรับคำสั่งซื้อและเช็คบิลด้วยระบบ Digital Billing และ Pre-Order ผ่านแอปพลิเคชัน

### แนวทางแก้ไขและประโยชน์ที่ผู้ประกอบการจะได้รับ
- ใช้ฐานข้อมูลจากแอปทำ ให้ร้านค้าระบุเงื่อนไขการแจกโปรโมชันได้เอง เช่น ให้ระบบคูปอง "ฟรีมิกเซอร์ 3 อย่าง" เฉพาะวันพุธ-พฤหัสบดี ไปยังผู้ใช้งาน 
- ใช้ระบบ Centralized Digital Billing ลูกค้าสามารถกดดูยอดบิลปัจจุบันของโต๊ะตัวเองผ่านแอปได้ตลอดเวลา และเมื่อต้องการเช็คบิล ระบบจะทำการหารค่าใช้จ่ายต่อหัว
- เพิ่มระบบให้ลูกค้ากดสั่งซื้อ "เซ็ตเปิดตี้" หรือโปรโมชันของร้านล่วงหน้าผ่านแอป เพื่อเป็นการันตีโต๊ะ 
- เพิ่ม้อกำหนด หากลูกค้ามาเลทเกินเวลาที่กำหนด (เช่น 30 นาที) ระบบจะปลดโต๊ะอัตโนมัติให้ลูกค้า Walk-in และร้านสามารถยึดมัดจำนั้นได้

## Product Roadmap: Nightout.day (Phase 1-4) [Executive Strategy]
### Phase 1: Legal-Proof MVP & Manual Validation (เดือน 1 - 3)
- Objective: พิสูจน์ Product-Market Fit ในพื้นที่นำร่อง 1 โซน ด้วยแนวทาง "รันระบบ Manual ให้อยู่รอด" เพื่อทดสอบกระบวนการทำงานและพฤติกรรมผู้ใช้จริง ก่อนลงทุนพัฒนาระบบอัตโนมัติเต็มรูปแบบ
- Customer-Facing:
- Budget-Based Search Engine: ค้นหาร้านและข้อเสนอตามงบประมาณจริงและจำนวนคนต่อกลุ่ม
- Table Booking Fee & Mixer Pre-order (Non-Alcohol): ชำระค่าธรรมเนียมการจองโต๊ะหรือสั่งซื้อเซ็ตอาหาร/มิกเซอร์ล่วงหน้า (ปลอดแอลกอฮอล์) เพื่อหลีกเลี่ยงข้อจำกัดทางกฎหมายเรื่องการขายแอลกอฮอล์ออนไลน์
- Manual Slip Upload & Split-Pay Link Generation: ระบบอัปโหลดสลิปการโอนเงินและสร้างลิงก์หารค่าใช้จ่ายสำหรับส่งต่อให้เพื่อนร่วมตี้ เพื่อรองรับกระบวนการตรวจสอบสลิปแบบ Manual
- Digital Age Verification (20+): ยืนยันตัวตนและอายุผู้ใช้งานก่อนเข้าถึงบริการการจองตามกฎหมาย
- Merchant & Ops-Facing:
- Ops War Room & Manual Verification System: แดชบอร์ดตรวจสอบสลิปและยืนยันยอดเงินโอนเข้าแอดมินล่วงหน้า พร้อมการการันตี SLA ตรวจสอบสลิปภายใน 3 นาที
- Table Management & Auto-Release Notification: จัดการสถานะโต๊ะ แจ้งเตือนล่วงหน้า 15 นาที และปลดโต๊ะอัตโนมัติหากเลทเกิน 30 นาที
- Resource & Action (Owner: PM & Ops): จัดตั้งทีม Ops War Room รองรับการตรวจสอบสลิปตลอดช่วงเวลาให้บริการ พร้อมพัฒนาระบบตรวจสอบแบบสืบค้นเร็ว
- KPIs:
- ร้านค้าพันธมิตร Active > 10 ร้าน ในพื้นที่นำร่อง
- Ops Verification SLA < 3 นาทีต่อสลิป และอัตรา No-Show ลดลงเหลือ < 5%
- Adoption Rate ของฟังก์ชัน Split-Pay > 50% ของยอดจองทั้งหมด

### Phase 2: Payment Automation & Automated GP Expansion (เดือน 4 - 6)
- Objective: เปลี่ยนผ่านจากการตรวจสอบ Manual สู่ระบบอัตโนมัติเต็มรูปแบบ ด้วยการเชื่อมต่อ API Payment Gateway (Omise / 2C2P) พร้อมสร้างรายได้ประจำผ่าน Automated GP (5-7%) และฟีเจอร์ Fast-Track
- Customer-Facing:
- API Payment Gateway Integration & Automated Split-Pay: รองรับการชำระเงินอัตโนมัติ (บัตรเครดิต/พร้อมเพย์) และหารค่าใช้จ่ายอัตโนมัติผ่าน Payment Gateway
- Fast-Track Entry & Premium Booking: ตัวเลือกชำระ Premium Booking Fee เพื่อการันตีโต๊ะทำเลดีและรับสิทธิ์เข้าใช้บริการแบบทางด่วน (ข้ามคิวหน้าร้าน)
- Merchant-Facing:Centralized Digital Billing Viewer: ระบบตรวจสอบรายการและยอดบิลรวมของโต๊ะแบบ Real-time ผ่านแอปพลิเคชัน
- 
- Automated GP Collection (5-7%): หักส่วนแบ่งค่าบริการอัตโนมัติผ่าน Payment Gateway ช่วยลดภาระการติดตามหนี้และเพิ่ม Cash Flow ให้แพลตฟอร์ม
- Dynamic Non-Alcohol Deals Engine: เครื่องมือให้ร้านค้าตั้งโปรโมชันกระตุ้น ยอดขายช่วง Off-Peak (เช่น ส่วนลดเซ็ตอาหาร/มิกเซอร์ หรือสิทธิพิเศษเช็คอินตรงเวลา)
- Resource & Action (Owner: Tech & BD): พัฒนาการเชื่อมต่อ Payment Gateway API ปรับสัญญาเก็บ GP และขยายฐานร้านค้าไปยังโซนยุทธศาสตร์ใหม่ (ทองหล่อ, เอกมัย, อารีย์)
- KPIs:
- รายได้ค่าธรรมเนียม GP เติบโตอย่างน้อย 20% MoM
- สัดส่วนการเลือกใช้บริการ Fast-Track > 15% ของยอดจองรวม

### Phase 3: Retention & Self-Serve Ads Ecosystem (เดือน 7 - 9)
- Objective: เพิ่ม Customer Lifetime Value (LTV) ของผู้ใช้ และเปิดช่องทางรายได้อัตรากำไรสูง (High Margin) จากโฆษณา B2B
- Customer-Facing:
- Cross-Venue Loyalty Program: ระบบสะสมแต้มส่วนกลางเพื่อนำไปแลกสิทธิพิเศษข้ามร้านค้า กระตุ้นอัตราการจองซ้ำ (Repeat Booking)
- AI-Powered Personalization & Vibe Match: ระบบแนะนำร้านค้าและสไตล์ดนตรีแบบเฉพาะบุคคลตามประวัติการใช้งาน
- Merchant-Facing:
- Self-Serve Sponsored Search Platform: ระบบ Bidding โฆษณาให้ร้านค้าซื้อพื้นที่โปรโมตและดันอันดับผลการค้นหาได้เอง
- Targeted CRM & Push Notification Engine: เครื่องมือส่งบรอดแคสต์โปรโมชันเจาะจงกลุ่มลูกค้าตามพฤติกรรมและความชอบ
- Resource & Action (Owner: Marketing & Tech): พัฒนา Ad Platform หลังบ้าน และพัฒนาระบบวิเคราะห์พฤติกรรมผู้ใช้ (User Data Analytics)
- KPIs:
- User Retention Rate > 30%
- สัดส่วนรายได้จากโฆษณา B2B Ads > 15% ของรายได้รวมทั้งหมด
### Phase 4: Data API Integration & B2B Expansion (เดือน 10 - 12+)
- Objective: ขยายผล Network Effect และต่อยอดข้อมูล Data Intelligence สู่ดีลความร่วมมือระดับองค์กร (Enterprise Partnerships) และบริการการเงิน
- B2B Integrations & Sponsorships:
- FMCG & Enterprise Data Sponsorships: นำเสนอข้อมูลภาพรวมการบริโภค (Aggregated & Anonymized Data) แก่แบรนด์สินค้าเครื่องดื่มและค่ายเพลงเพื่อร่วมทำแคมเปญการตลาด
- Safe Ride Home Affiliate Integration: เชื่อมต่อ API กับแอปพลิเคชันเดินทาง (Grab / LINE MAN) เพื่อรับส่วนแบ่งค่าโดยสารจากการเรียกรถกลับบ้านอย่างปลอดภัย
- Fintech & Ecosystem Expansion:
- In-App Digital Wallet Infrastructure: กระเป๋าเงินดิจิทัลเพื่อควบคุมการหมุนเวียนเงินในระบบ ลดต้นทุนค่าธรรมเนียม PG ระยะยาว และเพิ่มโซลูชันการชำระเงินลื่นไหล
- Resource & Action (Owner: CEO & BD): ปิดดีลพันธมิตรทางธุรกิจระดับองค์กร (FMCG/Ride-hailing) และยื่นขอใบอนุญาต/เตรียมความพร้อมทางด้าน Fintech
- KPIs:
- สัดส่วนรายได้จาก B2B Sponsorship & API Affiliates > 20% ของรายได้รวม

| 5. การแสดงผลรีวิว (Reviews) | - ส่วน Dashboard แอดมิน (Phase 1): ระบุว่าระบบรีวิวเปิดให้ใช้งานตั้งแต่ Phase 1 - ส่วนฝั่งลูกค้า (Phase 2): ระบุการเปิดระบบรีวิวให้ลูกค้าไว้ใน Phase 2 - ส่วนที่ยังไม่ได้ตัดสินใจ: ตั้งคำถามว่าดาวและรีวิวควรอยู่ Phase 1 หรือ 2 | Impact (Scope & Timeline): เป็น Scope Creep หากต้องทำระบบรีวิวใน Phase 1 ทีม Tech ต้องประเมิน Workload ใหม่ ควรฟันธงว่าจะเอาเข้า Sprint ของ Phase ไหน |
| 6. ฟีเจอร์ In-App Chat | - ส่วนฟีเจอร์เสริมฝั่งลูกค้า: ระบุในวงเล็บว่า "ทำเฟส 3-4" - ส่วนที่ยังไม่ได้ตัดสินใจ: ตั้งคำถามว่า In-App Chat อยู่ Phase ไหน | Impact (Scope Management): ต้องเคลียร์รายการฟีเจอร์รองออกจาก MVP เพื่อไม่ให้แย่ง Resource การพัฒนา Core Flow ใน Phase 1 |

### 2. ข้อเสนอแนะและสิ่งที่ต้องตัดสินใจ (Areas for Improvement & Critical Decisions)
เพื่อให้โครงการลดความเสี่ยงและสามารถดำเนินการ (Execute) ได้อย่างมีประสิทธิภาพ ขอเสนอแนะให้ทีมฟันธงในประเด็น "เรื่องที่ยังไม่ได้ตัดสินใจ" ดังต่อไปนี้:
- 1. ตัดสินใจเรื่อง Payment Gateway vs. Manual Transfer (Critical Priority)
- คำแนะนำ: เลื่อนการพัฒนา Payment Gateway (Split-Pay) จาก Phase 2 เข้ามาเป็น Critical Path ใน Phase 1 หากเป้าหมายคือการสเกลไประดับ 10,000 MAU การใช้ Admin ตรวจสลิป (Manual Escrow) จะทำให้เกิดคอขวดและผิดกฎหมาย ธปท.
- 2. ปรับปรุงนโยบายการเช็คอินและยึดมัดจำ (Customer Experience)
- คำแนะนำ: นโยบายยึดมัดจำ 100% ทันทีเมื่อเลท 30 นาที เป็นความเสี่ยงที่จะเกิดข้อพิพาท ควรปรับใช้ Business Logic: "อนุญาตให้กดขอต่อเวลาได้ 15 นาที" หรือ "นับว่าเช็คอินสำเร็จเมื่อสมาชิกคนแรกมาถึงร้าน" เพื่อรักษาฐานลูกค้า
- 3. นิยามคำว่า "มัดจำ" ให้ชัดเจน (Legal Risk)
- คำแนะนำ: ห้ามเปิดให้พรีออเดอร์แอลกอฮอล์ผ่านแอปเด็ดขาด (ตามคำแนะนำของฝ่ายกฎหมาย) ควรกำหนด Data Model ให้ชัดเจนว่าการมัดจำคือ "ค่าธรรมเนียมจองโต๊ะ (Table Fee)" หรือ "เซ็ตอาหาร/มิกเซอร์" เท่านั้น
- 4. กำหนดรอบชำระเงินให้ร้านค้า (Settlement Cycle)
- คำแนะนำ: หากใน Phase 1 ยังคงใช้ระบบ Escrow พักเงินไว้ที่บริษัท ต้องระบุรอบโอนเงินคืนร้านค้าให้ชัดเจน (เช่น T+1 หรือ T+3) ใน Terms of Service เพื่อป้องกันข้อพิพาทเรื่องกระแสเงินสดกับร้านค้า
- 5. ทำ Feature Pruning สำหรับ MVP Phase 1 (Scope Management)
- คำแนะนำ: ตัดฟีเจอร์รองออกจาก Phase 1 อย่างเด็ดขาด (Out of Scope) เช่น Wishlist, Social Proof, ระบบคะแนน/รีวิว, สะสมแต้ม On-Time Rewards เพื่อโฟกัส Resource ไปที่ Core Flow (ค้นหา -> จอง -> จ่ายเงิน -> สแกนเช็คอิน)

# แท็บ: Roadmap Business

Roadmap Business: Strategic Execution & Growth Playbook
Version: Comprehensive Strategy (Aligned with Legal, Ops, Sales & Growth)

### 1. Executive Summary (สรุปประเด็นสำคัญ)
แผนธุรกิจฉบับนี้ถูกปรับโครงสร้างใหม่แบบบูรณาการ (Integration) เพื่อแก้ปัญหาความขัดแย้งของแผนเดิมที่ระบบ Manual ตรวจสลิปไม่สามารถ Scale ได้ (Ops Bottleneck) และมีความเสี่ยงขั้นวิกฤตทางกฎหมาย (Legal Critical Risk)

จุดชี้เป็นชี้ตาย (Make or Break) คือ Phase 1 ที่ต้องจำกัดสเกลเพื่อพิสูจน์ Product-Market Fit (PMF) ภายใต้ร่มกฎหมาย (Legal-Proof) ก่อนจะเร่งเครื่องเข้าสู่ Phase 2 ด้วยระบบ API Payment อัตโนมัติเพื่อสร้างกระแสเงินสด (Cash Flow) จาก GP 5-7% และสเกลสู่การทำกำไรขั้นสูงจากรายได้โฆษณา (B2B Ads) ใน Phase 3-4

### 2. Situation (สถานการณ์ปัจจุบัน)
- เป้าหมาย: สร้างแพลตฟอร์ม One-Stop Nightlife แก้ปัญหาลูกค้างบจำกัด (Budget Search) และร้านค้าโดนเทโต๊ะ (No-show)
- ปัญหาโครงสร้าง: แผนเดิมต้องการผู้ใช้ 10,000 MAU แต่ใช้แอดมินคนตรวจสลิป ซึ่งตามทฤษฎีแถวคอย (Queuing Theory) SLA 3 นาทีจะล้มเหลวทันทีในช่วง Peak Hour (17:00-21:00 น.)
- ปัญหาความเสี่ยง: การรับ "พรีออเดอร์เบียร์" และการรับเงินเข้าบริษัทแทนร้านค้า (Manual Escrow) ละเมิดพ.ร.บ.ควบคุมเครื่องดื่มแอลกอฮอล์ และกฎหมาย ธปท. โดยตรง
### 3. Analysis (การวิเคราะห์เชิงลึก 4 มิติ)
#### 3.1 Legal (ประเด็นกฎหมายและความเสี่ยง)
- พ.ร.บ. ควบคุมเครื่องดื่มแอลกอฮอล์: การขายแอลกอฮอล์ออนไลน์แบบลดแลกแจกแถมผิดกฎหมายเด็ดขาด วิธีแก้:ต้องเปลี่ยนนิยาม SKU ในระบบเป็น "ค่ามัดจำจองโต๊ะ (Table Fee)" และ "เซ็ตมิกเซอร์/อาหาร" เท่านั้น
- พ.ร.บ. ระบบการชำระเงิน: การรับโอนเงินเข้าบัญชีบริษัทมีความเสี่ยงหาก Scale ใหญ่ วิธีแก้: ใช้โมเดลนี้เฉพาะ Phase 1 ในสเกลทดสอบ (5-10 ร้าน) จากนั้นต้องย้ายไปใช้ API Payment (Omise/2C2P) ที่ตัดเงินเข้ากระเป๋าร้านค้าโดยตรง (Split Payment) ใน Phase 2
- Liability & PDPA: ป้าย "Safety Verified" ทำให้บริษัทรับความเสี่ยงทางละเมิดร่วมกับร้าน วิธีแก้: เปลี่ยน wording เป็น "ข้อมูลอ้างอิงจากร้านค้า (Merchant Declared)" และบังคับมี Pop-up ยืนยันอายุ (20+) พร้อมขอ Consent (PDPA) ตั้งแต่ลงทะเบียน
#### 3.2 Business & Financial Impact (ผลกระทบทางธุรกิจและการเงิน)
- Unit Economics: การเก็บ GP 5-7% จากยอดมัดจำ (สมมติมัดจำ 500 บ. = รายได้ 30 บ./โต๊ะ) เป็น Margin ที่ต่ำ แพลตฟอร์มจะยังไม่ทำกำไรจากการเก็บ GP เพียงอย่างเดียว
- Financial Strategy: Phase 1 ถือเป็น "Cost Center" เพื่อหา PMF ธุรกิจจะเริ่มคุ้มทุน (Break-even) เมื่อเข้าสู่ระบบ Automation (Phase 2) ที่รับปริมาณ Volume ได้มหาศาล และจะทำกำไรสุทธิสูง (High Margin) จาก B2B Sponsored Ads และ Data Monetization ใน Phase 3-4
#### 3.3 Sales (กลยุทธ์การขาย / B2B)
- Target (ICP): ผับ บาร์ ร้านนั่งชิล ขนาดกลาง-เล็ก ที่รับจองผ่าน LINE และมีปัญหา No-show
- Phase 1 (Acquisition): เสนอ Value Proposition "ลด No-show ฟรี 3 เดือน" โดยชูจุดแข็งว่าแพลตฟอร์มเป็น "คนรับหน้า" บังคับลูกค้าจ่ายมัดจำ ร้านไม่ต้องเสี่ยงทวงเงินเอง
- Phase 2 (Negotiation & Closing): เมื่อหมดโปรใช้ฟรี การดึงร้านเข้าสู่การเก็บ GP 5-7% ต้องใช้ Data Leverage นำข้อมูลยอดการมาเช็คอินจริงและฐานลูกค้ารายใหม่ไปเจรจาต่อรอง หากร้านไม่ยอม (Walk-away point) ให้ระงับสถานะร้านแนะนำ
#### 3.4 Marketing (กลยุทธ์การตลาด / Growth)
- Acquisition Loop: ไม่ใช้การสาดงบยิงแอด แต่ใช้ฟีเจอร์ "Split-Pay Link" (ลิงก์หารเงิน) เป็น Viral Mechanism — เมื่อ 1 คนจอง ต้องแชร์ลิงก์เข้า LINE กลุ่มให้เพื่อนอีก 4 คน (1 User acquires 4 Users แบบ Organic)
- Retention: ใช้ "On-Time Check-in Rewards" (เช่น มาตรงเวลาแจกมิกเซอร์ฟรี) เพื่อดึงพฤติกรรมลูกค้า และใช้ AI Recommendation ใน Phase 3 กระตุ้นยอด Booking วันธรรมดา
- Upsell: เปิดฟีเจอร์ "Fast-Track Entry" เจาะกลุ่ม First Jobber (ยอมจ่าย Premium 50-100 บาท/บิล เพื่อลัดคิวหน้าร้าน)
### 4. Recommendation (ข้อเสนอแนะเชิงกลยุทธ์ที่ดีที่สุด)
"Do things that don't scale (in Phase 1) to build a system that scales infinitely (in Phase 2)."
ข้อเสนอแนะคือ ให้ตัดฟีเจอร์ที่เกินความจำเป็นใน Phase 1 ออก (เช่น In-App Chat, Social Proof, AI Chat) เพื่อให้ทีม Tech ทุ่มเทสรรพกำลังไปที่ Core Flow (ค้นหางบ -> จอง -> อัปโหลดสลิป -> QR สแกน) และเริ่มพัฒนาระบบ Payment API คู่ขนานไว้เลยเพื่อหนีความเสี่ยงทางกฎหมายให้เร็วที่สุด

### 5. Action Plan (แผนปฏิบัติการตาม Phase)

- Sales/BD: ขยายทีมลุยโซนที่ 2 (เช่น ทองหล่อ, อารีย์) พร้อมเจรจาเก็บ GP ร้านเก่า

#### Phase 3: Retention & Self-Serve Ads Ecosystem (เดือน 7-9)

- Sales: เปิดระบบ Bidding B2B Ads ให้ร้านค้าเติมเงินซื้อพื้นที่ดันอันดับ "ร้านแนะนำ (Sponsored)"

- เป้าหมาย: Data Monetization | Ecosystem Partnerships

- BD/Tech: เชื่อม API กับแอปเรียกรถ (Grab/LINE MAN) ขึ้นปุ่ม "เรียกรถกลับบ้าน" พร้อมเก็บ Affiliate %
### 6. KPI (ตัวชี้วัดความสำเร็จผ่าน AARRR Framework)
ต้องฝัง Tracking Code ในแอปตั้งแต่วันแรก:

- Acquisition: Cost Per Acquisition (CPA) < 50 บาท/User
- Activation: Search-to-Booking Conversion Rate > 10%
- Retention: 30-Day Repeat Booking Rate > 30% (ตัวชี้วัดความอยู่รอด)
- Revenue: GP Revenue เติบโต > 20% MoM (เริ่มวัดใน Phase 2)
- Productivity: Ops SLA ตรวจสลิป < 3 นาที (Phase 1) และเวลาตัดบัตรเครดิต/API สำเร็จ < 1 นาที (Phase 2)
### 7. Risk (ความเสี่ยงและวิธีป้องกัน)
- Customer Risk (ข้อพิพาทเรื่องการยึดมัดจำ):
- ปัญหา: กฎยึดมัดจำ 100% หากเลท 30 นาที ก้าวร้าวเกินไป อาจทำให้ลูกค้าโกรธและเลิกใช้แอป

# แท็บ: รีวิว project

#### Executive Summary — สรุปประเด็นสำคัญ
แผนการปล่อย MVP Phase 1 ของ Nightout.day ด้วยระบบ Manual Escrow (คนตรวจสลิป) มีความขัดแย้งทางคณิตศาสตร์กับเป้าหมายการเติบโตระดับ 10,000 - 20,000 MAU เมื่อนำ Queuing Theory (ทฤษฎีแถวคอย) มาคำนวณ ภาระงานช่วง Peak Hour จะทำให้ SLA 3 นาทีล้มเหลวทันทีหากไม่มี Admin สแตนด์บายพร้อมกันอย่างน้อย 6 คน นอกจากนี้ Unit Economics ชี้ให้เห็นว่าโมเดลรายได้จาก GP 5-7% ของยอดมัดจำเพียงอย่างเดียว ไม่เพียงพอต่อ Burn Rate ของทีมงาน 12 คน การ Pivot ไปใช้ API Payment (Option 3) จึงไม่ใช่แค่ทางเลือกเพื่อเลี่ยงกฎหมาย แต่เป็น "ความจำเป็นทางโครงสร้างข้อมูลและกระแสเงินสด"

#### Business Question — คำถามหรือปัญหาที่วิเคราะห์
- ระบบปฏิบัติการแบบ Manual ใน Phase 1 สามารถรองรับเป้าหมาย User Acquisition ที่ 10,000 MAU ได้จริงหรือไม่?
- โครงสร้างรายได้ (Unit Economics) จาก GP 5-7% คุ้มค่าและเพียงพอต่อการอยู่รอดของธุรกิจ (Runway) หรือไม่?
- เราควรออกแบบ Data Tracking และ KPI อย่างไรเพื่อวัดผล Product-Market Fit (PMF) ให้แม่นยำที่สุด?
#### Data Overview — แหล่งข้อมูล ช่วงเวลา และข้อจำกัด
- แหล่งข้อมูล: เอกสาร Project Charter, WBS, และ Legal Review ของ Nightout.day
- ข้อมูลทีมงาน: บุคลากร 12 คน (Founder 3, Tech 4, QA 2, Content 2, PM 1)
- สมมติฐานเป้าหมาย: 10,000 MAU (ขั้นต่ำ) ถึง 20,000 MAU (ตาม Business Roadmap), ร้านค้า 50 ร้าน
- ข้อจำกัดของข้อมูล: ข้อมูลการเงิน (เงินเดือน, ค่าเซิร์ฟเวอร์, งบการตลาด) ไม่ได้ระบุชัดเจน จึงใช้ค่าประมาณการขั้นต่ำเพื่อทำ Sensitivity Analysis
#### Key Findings — ผลการวิเคราะห์และตัวเลขสำคัญ
1. Operational Bottleneck Analysis (วิเคราะห์คอขวดระบบหลังบ้าน)

- สมมติฐานการคำนวณ: เป้าหมาย 10,000 MAU -> สมมติมี Conversion Rate จองโต๊ะที่ 10% = 1,000 Bookings/เดือน (เฉลี่ย 33 Bookings/วัน)
- หากขยับไปที่เป้าหมายสูงสุด 20,000 MAU และลูกค้า 1 คนจอง 1 ครั้ง/เดือน = 20,000 Bookings/เดือน (เฉลี่ย 666 Bookings/วัน)
- วิเคราะห์ Peak Hour (17:00 - 21:00 น. = 4 ชั่วโมง หรือ 240 นาที): สมมติ 70% ของ Traffic เกิดขึ้นเวลานี้ = 466 Bookings
- ผลลัพธ์ (SLA 3 นาที/สลิป): ต้องใช้เวลาตรวจรวม 1,398 นาที ภายในกรอบเวลา 240 นาที แปลว่าทีม Content/Admin ต้องทำงานพร้อมกันอย่างน้อย 5.8 คน (ปัดเป็น 6 คน) โดยไม่หยุดพัก ระบบ Manual จึงเป็น "ความเสี่ยงต่อความล้มเหลวเชิงปฏิบัติการ (Operational Failure)" อย่างหลีกเลี่ยงไม่ได้
2. Unit Economics & ROI Analysis (วิเคราะห์ความคุ้มค่า)

- พฤติกรรมลูกค้า: กลุ่มละ 4-7 คน งบ 300 บาท/คน = ยอดบิลรวมประมาณ 1,500 บาท/โต๊ะ
- โครงสร้างรายได้: การเก็บ GP 5-7% คำนวณจาก "ยอดมัดจำ/เซ็ตเปิดตี้" (สมมติมัดจำโต๊ะละ 500 บาท)
- Net Revenue: GP 6% ของ 500 บาท = 30 บาท / 1 Booking (หากหักค่าธรรมเนียม Payment Gateway 3% จะเหลือ Net ~15 บาท)
- ความอยู่รอดของบริษัท: หากประเมิน Burn Rate ของทีม 12 คน ขั้นต่ำที่ 250,000 บาท/เดือน บริษัทต้องมียอดจองถึง 8,333 - 16,666 Bookings/เดือน จึงจะถึงจุดคุ้มทุน (Break-even)
3. Feature Bloat vs. PMF Verification

- ข้อมูลชี้ว่าเอกสารพยายามยัดฟีเจอร์ที่ไม่สร้าง Core Value ลงใน Phase 1 เช่น Crowd Status, In-App Chat, ระบบสะสมแต้ม ซึ่งเป็นการใช้ Data Storage และ API Call อย่างสูญเปล่า และดึงเวลาของทีม Tech (พี, บิว, ที, หนุ่ย) ออกจากการทำ Payment API
#### Root Cause / Interpretation — สาเหตุหรือคำอธิบาย
ปัญหาหลักเกิดจาก "การประเมินภาระทาง Data และ Transaction ต่ำเกินไป" แนวคิด "The Hustle Phase (ทำ Manual ไปก่อน)" ใช้ได้กับสเกล < 10 ร้านค้า แต่ด้วยเป้าหมายทางการตลาด (Marketing Subsidy) ที่ต้องการลาก Traffic หลักหมื่น ระบบฐานข้อมูลคน (Human Database) จะพังทลาย โครงสร้างรายได้ที่แคบ (เก็บ GP แค่มัดจำ ไม่ใช่ทั้งบิล) ทำให้ LTV (Lifetime Value) ของลูกค้า 1 คนต่ำมาก ธุรกิจจึงต้องพึ่งพาปริมาณมหาศาล (Volume-heavy) ซึ่งไม่สอดคล้องกับระบบ Manual

#### Business Impact — ผลกระทบต่อธุรกิจ
- High Risk of Churn: หากลูกค้าโอนเงินแล้ว E-Ticket ไม่ออกภายใน 3 นาที (เพราะคิว Admin ล้น) ลูกค้าจะเกิด Panic และเปลี่ยนร้าน
- Negative Cash Flow: รายได้จาก B2C (การจอง) เป็นธุรกิจ Margin ต่ำ การใช้เวลาพัฒนาฟีเจอร์ที่ไม่จำเป็น จะทำให้ Cash Runway หมดก่อนที่บริษัทจะปลดล็อกระบบ Ads (B2B) ใน Phase 3
#### Recommendations — ข้อเสนอแนะที่จัดลำดับความสำคัญ
Priority 1: ปรับโครงสร้าง Data & Tech สู่ API Automation (เร่งด่วนที่สุด)

- Action: เลิกทำ Manual Slip Validation โยก Resource ของ Backend ไปพัฒนาการเชื่อมต่อ Omise/2C2P (Split-Pay) ทันที
- เหตุผล: แก้ไขคดีอาญา (Escrow) และปลดล็อกเพดานการสเกล Transaction
Priority 2: ปรับ Data Definition ของคำว่า "มัดจำ"

- Action: เปลี่ยนเงื่อนไข Data ใน Backend จาก "Pre-order แอลกอฮอล์" เป็น SKUs ที่เป็น Non-Alcohol (เช่น Table Fee 200 บาท, มิกเซอร์เซ็ต 300 บาท)
Priority 3: ขยับแผน Data Monetization (B2B Ads) ขึ้นมา Phase 2

- Action: เนื่องจาก Unit Economics ของการเก็บ GP ไม่พอเลี้ยงบริษัท ต้องเร่งเปิดฟีเจอร์ "Sponsored Search" ให้ร้านค้าซื้อโฆษณาดันอันดับโดยเร็วที่สุด
Priority 4: A/B Testing นโยบายการยึดมัดจำ (Auto-Release)

- Action: นโยบายยึดเงิน 100% เมื่อเลท 30 นาที ก้าวร้าวเกินไป ควรเก็บข้อมูล (Data Logging) เวลาเช็คอินจริง เพื่อประเมินค่าเฉลี่ยความล่าช้า (Average Delay Time) และทำ A/B Test ด้วยการส่ง SMS เตือนที่ 15 และ 30 นาที พร้อมให้ปุ่ม "กดต่อเวลา 15 นาที" (ลดข้อพิพาท)

#### Success Metrics — ตัวชี้วัดและวิธีประเมินผล (AARRR Framework)
เพื่อวัดผล Phase 1 (PMF) ให้ใช้ Metric ดังต่อไปนี้ (ต้องฝัง Tracking Code ให้พร้อมก่อน Launch):

- Acquisition:
- Metric: Cost Per Acquisition (CPA)
- สูตร: Total Marketing Spend / New Registered Users (เป้าหมาย: < 50 บาท)
- Activation:
- Metric: Search-to-Booking Conversion Rate
- สูตร: (Unique Users จองโต๊ะสำเร็จ / Unique Users ที่ใช้ช่องค้นหา) * 100 (เป้าหมาย: > 10%)
- Retention (ตัวชี้วัดความเป็นความตาย):
- Metric: 30-Day Repeat Booking Rate
- สูตร: (Users ที่กลับมาจองครั้งที่ 2 ภายใน 30 วัน / Users ที่จองครั้งแรก) * 100 (เป้าหมาย: > 30%)
- Revenue:
- Metric: Gross Merchandise Value (GMV) & Take Rate
- สูตร: ยอดรวมเงินมัดจำทั้งระบบ และ (Total Net GP / GMV) * 100
- Productivity (Operational Health):
- Metric: Payment Completion Time
- สูตร: Timestamp (Payment Confirmed) - Timestamp (Click Book) (เป้าหมาย: ตัดเงิน API จบใน < 1 นาที แทน SLA คน 3 นาที)

	•	ขนาดกลุ่ม: ไปกันเป็นกลุ่มใหญ่ (5-10 คนขึ้นไป) มักจะมี "ตัวเปิด/แกนนำ" 1 คนที่เป็นคนคอยหาร้านและจองโต๊ะ
	•	การตัดสินใจ: มีความอ่อนไหวเรื่องราคา (Price-sensitive) ต้องคำนวณงบให้ชัดเจนก่อนไปหารกัน และชอบโปรโมชันแบบ "มาก่อน 3 ทุ่มได้โปรฯ ชุดใหญ่"

	•	สไตล์ร้านที่ชอบ (Venue Preferences):
	•	ผับ/ร้านนั่งชิลดนตรีสดที่จังหวะสนุก (EDM, T-Pop, อินดี้แมส)
	•	ร้านที่มี "เซ็ตเปิดตี้" คุ้มๆ บรรยากาศพลุกพล่าน โต๊ะเยอะ แสงสีจัดเต็ม
	•	Pain Points (ปัญหาที่เจอ):
	•	รวมตัวยาก นัดแล้วเพื่อนมาเลท โต๊ะหลุด
	•	งบบานปลาย สั่งเพลินแล้วตอนหารบิลจ่ายไม่ไหว
	•	หาร้านที่มีโต๊ะพอสำหรับ 10 คนในคืนวันศุกร์ยาก
	•	ฟีเจอร์ใน BarBook ที่ตอบโจทย์กลุ่มนี้ (Feature Mapping):
	•	Budget Calculator (ตัวคำนวณงบ): จัดการความกังวลเรื่องราคา ให้เห็นยอดหารต่อหัวชัดเจนตั้งแต่ก่อนไป
	•	Share to Gang: ส่งตั๋วเข้า LINE กลุ่มให้เพื่อนตามพิกัดมาได้เลย ลดภาระคนจอง
	•	Crowd Status: ดูสถานะความแน่นร้าน เพื่อหนีร้านที่คนล้นจนไม่มีที่ยืน

# แท็บ: วิเคราะห์โดย claude

เอกสารมีแกนไอเดียที่ดีมาก โดยเฉพาะการค้นหาร้านตามงบ และการใช้เซ็ตพรีออเดอร์เป็นมัดจำ แต่ผมเจอจุดที่ควรแก้ก่อนเอาไปเสนอหรือลงมือทำจริง ไล่จากเรื่องที่หนักที่สุดลงไปครับ
#### 1. ความเสี่ยงด้านกฎหมาย (สำคัญที่สุด แต่แผนยังไม่พูดถึงเลย)
การขายแอลกอฮอล์ผ่านแอป ฟีเจอร์ "พรีออเดอร์เบียร์ 1 ลัง" คือการขายเครื่องดื่มแอลกอฮอล์ผ่านช่องทางอิเล็กทรอนิกส์ ซึ่งประกาศกระทรวงสาธารณสุขปี 2563 ห้ามไว้ ถ้าโดนตีความ ฟีเจอร์ที่เป็นหัวใจของแผนจะใช้ไม่ได้ทันที ทางออกที่ปลอดภัยกว่าคือขาย "แพ็กเกจโต๊ะ / ค่ามัดจำโต๊ะ / มิกเซอร์ / อาหาร" แทน แล้วให้ลูกค้าไปสั่งเหล้าที่ร้านเอง
โปรโมชันลดราคาแอลกอฮอล์และการโฆษณา โปรอย่าง "เบียร์ 3 ขวดลด 20%", "4 จ่าย 3" หรือแบนเนอร์แบรนด์เหล้าใน Phase 2 และการขายดาต้าให้แบรนด์เหล้าใน Phase 4 ล้วนชน พ.ร.บ.ควบคุมเครื่องดื่มแอลกอฮอล์ ทั้งมาตรา 30 เรื่องห้ามขายแบบลดราคาหรือแถม และมาตรา 32 เรื่องโฆษณา โปรที่เน้น "มิกเซอร์ฟรี" ในแผนจึงฉลาดกว่า เพราะมิกเซอร์ไม่ใช่แอลกอฮอล์ กฎหมายนี้มีการแก้ไขในปี 2568 ด้วย ผมแนะนำให้ปรึกษานักกฎหมายก่อนล็อกฟีเจอร์ครับ
อายุผู้ใช้ กลุ่มเป้าหมายคือนักศึกษา แต่ปี 1–2 อายุ 18–19 ปียังไม่ถึงเกณฑ์ 20 ปี การทำตลาดรอบมหาลัยโดยไม่มีระบบยืนยันอายุเสี่ยงทั้งทางกฎหมายและภาพลักษณ์ ควรมีการยืนยันอายุตอนสมัคร และให้ร้านตรวจบัตรตอนสแกน QR
การถือเงินมัดจำ การรับเงินเข้าบัญชีบริษัทแล้วโอนต่อให้ร้าน อาจเข้าข่ายธุรกิจรับชำระเงินแทนตาม พ.ร.บ.ระบบการชำระเงิน เอกสารพูดเรื่องนี้แล้วในส่วน Executive Summary แต่ยังไม่ได้อัปเดตกลับไปที่ตาราง MVP (ดูข้อ 5)
PDPA ข้อมูลพฤติกรรมการดื่มเป็นข้อมูลที่อ่อนไหว ถ้าจะขาย insight ให้แบรนด์ ต้องวางระบบขอความยินยอมตั้งแต่วันแรก
#### 2. มุมลูกค้า
ใครเป็นคนจ่ายมัดจำ ปัจจุบันระบบออกแบบให้ "แกนนำ" จ่ายทั้งก้อน แล้วไปทวงเงินเพื่อนเอง ซึ่งเป็น pain point ใหญ่ของกลุ่มวัยรุ่น ผมแนะนำให้ทำ Split-pay ตั้งแต่ตอนจอง คือแชร์ลิงก์เข้า LINE กลุ่มแล้วให้แต่ละคนจ่ายส่วนตัวเอง ฟีเจอร์นี้ต่อยอดจาก Share to Gang ได้ตรงๆ ช่วยดึงคนโหลดแอปเพิ่ม และกลายเป็นจุดขายที่คู่แข่งไม่มี
กฎยึดมัดจำ 100% เมื่อเลท 30 นาทีโหดเกินไป ในกรุงเทพฯ แค่ฝนตกหรือรถติดก็เลทแล้ว ถ้าลูกค้าโดนยึดเงินครั้งแรก มีโอกาสสูงที่จะเลิกใช้และไปรีวิวแย่ในโซเชียล ควรเพิ่ม 4 อย่างนี้:
- ให้นับว่ามาแล้วเมื่อสมาชิกคนแรกเช็คอิน
- แจ้งเตือนล่วงหน้าที่ 15 นาที
- ให้ขอต่อเวลาได้ 1 ครั้ง
- มีนโยบายยกเลิกที่ชัดเจน เช่น ยกเลิกล่วงหน้า X ชั่วโมงได้เงินคืน
ถ้าร้านผิดเอง ลูกค้าได้อะไร แผนพูดแต่กรณีลูกค้าเบี้ยว แต่ไม่พูดกรณีร้านให้โต๊ะคนอื่นไป ร้านปิดกะทันหัน หรือราคาหน้าร้านไม่ตรงกับในแอป ต้องมีระบบคืนเงินและการจัดการข้อพิพาทที่ฝั่งลูกค้ามั่นใจได้ ไม่อย่างนั้นความน่าเชื่อถือจะเป็นแบบด้านเดียว
ฟีเจอร์ที่ขัดกับจุดยืน "ร้านงบน้อย" Surge Pricing กับ Smart Upselling ที่ยิงโปรเบียร์ไปยังโต๊ะที่นั่งนาน จะทำให้ลูกค้ารู้สึกว่าแอปไม่ได้อยู่ข้างเขาแล้ว ทั้งที่จุดขายคือช่วยคุมงบ Upselling ยังเสี่ยงเรื่องดราม่า "แอปเร่งให้วัยรุ่นดื่มเพิ่ม" ด้วย ควรตัดออก หรือเปลี่ยนเป็นโปรอาหารหรือมิกเซอร์แทน
ความปลอดภัยยังเป็นแค่ข้อมูล ยังไม่ใช่ฟีเจอร์ Safety เป็นหนึ่งใน pain point ที่ระบุไว้ แต่ตอนนี้มีแค่ป้าย ✅/❌ ควรเพิ่มของที่ใช้ได้จริงตอนเที่ยว เช่น แชร์ตำแหน่งให้เพื่อน ปุ่มขอความช่วยเหลือ หรือเช็คว่าทุกคนกลับถึงบ้านแล้ว และควรย้ายปุ่มเรียกรถจาก Phase 4 มาไว้ Phase 1 ในรูปแบบ deep link ธรรมดา ไม่ต้องรอดีล affiliate
ป้าย "ยืนยันโดย NightOut" เป็นภาระรับผิด ถ้ามีเหตุร้ายในร้านที่ติดป้ายนี้ บริษัทอาจถูกพาดพิง ควรระบุวันที่ตรวจล่าสุด และเขียนขอบเขตความรับผิดให้ชัด
เพลงประกอบโปรไฟล์ร้าน มีประโยชน์น้อย และถ้าใช้เพลงมีลิขสิทธิ์ต้องจ่ายค่าไลเซนส์ ควรใช้เพลง royalty-free หรือคลิปบรรยากาศที่ร้านอัดเองแทน
#### 3. มุมร้านค้า
ทำไมร้านเล็กต้องใช้ ร้านเล็กส่วนใหญ่รับจองผ่าน LINE หรือ IG อยู่แล้ว และบางร้านไม่รับจองเลย แผนยังไม่ได้ตอบว่าทำไมร้านต้องเปลี่ยนมาใช้แอป นอกจากเรื่องลด no-show ซึ่งร้านเล็กหลายร้านอาจไม่ได้เจอปัญหานี้หนักนัก
ร้านจะดึงลูกค้าออกไปจองตรง (Disintermediation) เมื่อเก็บ GP เฉพาะยอดพรีเพด และร้านรู้จักลูกค้าแล้ว ร้านมีแรงจูงใจบอกลูกค้าว่า "ครั้งหน้าทักไลน์ร้านมาเลย" ต้องมีของที่ทำให้อยู่ในแอปคุ้มกว่า เช่น แต้มสะสมข้ามร้าน หรือ CRM ที่ร้านใช้ได้เฉพาะลูกค้าที่จองผ่านแอป
ภาระพนักงานสวนทางกับที่สัญญาไว้ แผนบอกว่าพนักงานร้านเล็กยุ่งมากช่วงพีค แต่กลับให้พนักงานอัปเดตผังโต๊ะและ Crowd Status แบบ real-time เองในช่วงเดียวกันนั้น ข้อมูลจะไม่ถูกอัปเดตแน่นอน ควรคำนวณสถานะให้อัตโนมัติจากยอดจองและเช็คอิน แล้วให้ร้านแค่กดแก้เมื่อจำเป็น
Centralized Digital Billing ใน Phase 2 เร็วเกินไป ต้องเชื่อมกับ POS ของแต่ละร้าน ซึ่งร้านเล็กมักใช้บิลกระดาษหรือ POS คนละยี่ห้อ งานหนักมากเมื่อเทียบกับประโยชน์ที่ได้ช่วงแรก
ร้านอ้างว่าลูกค้าไม่มาเพื่อยึดมัดจำ ต้องมีหลักฐานการเช็คอินที่ทั้งสองฝ่ายตรวจสอบได้ และมีขั้นตอนอุทธรณ์
ร้านได้มัดจำที่ยึดไป 100% แพลตฟอร์มไม่ได้อะไร ลองพิจารณาแบ่งส่วนหนึ่ง หรืออย่างน้อยเก็บไว้เป็นค่าบริการ
ภาระตอนเริ่มต้น การกรอกเมนูและราคาซึ่งเปลี่ยนบ่อย ต้องมีทีมช่วยลงข้อมูลให้ (แผนมีพูดถึงนิดหน่อยในส่วนแอดมิน) และต้องกำหนดว่าถ้าราคาไม่ตรง ใครรับผิดชอบ
#### 4. มุมธุรกิจและตัวเลข
ยังไม่มี Unit Economics ลองคิดคร่าวๆ: โต๊ะ 8 คน จ่ายพรีเพด 1,000 บาท × GP 6% = 60 บาท หักค่า gateway เหลือราว 40–50 บาทต่อการจอง ถ้าได้ 3,000 การจองต่อเดือน รายได้จะอยู่ราว 1.2–1.5 แสนบาท ซึ่งอาจไม่พอเลี้ยงทีม แปลว่ารายได้จากโฆษณาสำคัญกว่าที่แผนวางไว้ ควรมีตารางคำนวณ CAC, จำนวนการจองต่อร้าน, รายได้ต่อการจอง และจุดคุ้มทุน
ปัญหาไก่กับไข่ ถ้ามีร้านแค่ 5–10 ร้าน ฟีเจอร์ค้นหาตามงบจะได้ผลลัพธ์น้อยจนดูไม่มีประโยชน์ ควรใส่ร้านที่ยังไม่เป็นพาร์ทเนอร์แบบโชว์ข้อมูลอย่างเดียวไว้ก่อน แล้วเปิดให้จองได้เฉพาะร้านพาร์ทเนอร์
ปัจจัยตามฤดูกาลที่ไม่ได้คิดไว้ ช่วงปิดเทอม ช่วงสอบ วันพระใหญ่และวันเลือกตั้งที่ห้ามขายเหล้า และเวลาที่กฎหมายอนุญาตให้ขาย ล้วนกระทบยอดจองของกลุ่มนักศึกษาโดยตรง
MVP ใหญ่เกินไป Phase 1 มีทั้ง AI chat, แผนที่, event, ระบบดาว, Safety verification, เพลง, ผังโต๊ะ, แต้มสะสม และอื่นๆ เกินกว่าจะทำเสร็จใน 3 เดือนแล้วยังวัดผลได้ชัด ผมแนะนำให้เหลือแกนแค่นี้: ค้นหาตามงบ, จองพร้อมจ่ายมัดจำแบบหารกัน, QR เช็คอิน, รีวิว ที่เหลือเลื่อนไป Phase ถัดไป
ระบบดาวช่วงแรกจะไม่นิ่ง เพราะจำนวนเช็คอินยังน้อย ควรใช้ค่าเฉลี่ยแบบถ่วงน้ำหนัก (Bayesian average) หรือซ่อนดาวไว้จนกว่าจะมีรีวิวครบจำนวนขั้นต่ำ
คู่แข่งแคบเกินไป แผนเทียบกับ Nightify อย่างเดียว ซึ่งคนอ่านอาจไม่รู้จัก ควรอธิบายสั้นๆ ว่าคืออะไร และเพิ่มคู่แข่งจริงในชีวิตลูกค้า เช่น TikTok/IG ที่ใช้หาร้าน, LINE OA ที่ใช้จองร้าน, Google Maps, Wongnai และ Hungry Hub
KPI ยังขาดตัวชี้วัดการกลับมาใช้ซ้ำ ควรเพิ่มอัตราการจองซ้ำ, retention ของร้าน และจำนวนการจองต่อร้านต่อสัปดาห์ ซึ่งบอกได้ว่าธุรกิจอยู่รอดหรือไม่ ชัดกว่า MAU
#### 5. ความไม่สอดคล้องภายในเอกสาร
- Phase 1 มีสองเวอร์ชันที่ขัดกัน เวอร์ชันแรกคือเดือน 1–4 เป้า 300 ร้าน และ 20,000 MAU อีกเวอร์ชันคือเดือน 1–3 เป้า 5–10 ร้าน ต่างกันหลายสิบเท่า และเดือน 4 ก็ทับกับ Phase 2
- ระบบรับเงินพูดไม่ตรงกัน Executive Summary แนะนำ Payment Gateway แต่ตาราง MVP ยังเขียนว่า "โอน PromptPay + อัปโหลดสลิป" และส่วนแอดมินเขียนว่า "เข้า PromptPay ของ NightOut"
- KPI สองตัวไม่สอดคล้องกัน Check-in > 85% กับ No-show < 5% เหลือช่องว่าง 10% ที่ไม่รู้ว่าคืออะไร (ยกเลิก? เลื่อน?) ต้องนิยามให้ชัด
- มีชื่อ "BarBook" หลุดมา ในส่วน persona น่าจะเป็นชื่อเก่าหรือมาจากเอกสารอื่น
- หัวข้อ Pain Points ข้อ 2 มีแต่หัวข้อ ไม่มีเนื้อหา และหัวข้อ "แนวทางแก้ไข" มีคำว่า "แก้ปัญหา" ค้างอยู่เฉยๆ
- ตาราง MVP ไม่ได้ระบุ Phase ทำให้ไม่รู้ว่าฟีเจอร์ไหนต้องเสร็จเมื่อไร
- ยังขาดเรื่องทีม งบประมาณ และแหล่งเงินทุน ถ้าจะนำเสนอนักลงทุน ส่วนนี้จำเป็น

# แท็บ: Legal กฎหมาย

#### 1. ประเด็นทางกฎหมายหลัก (Legal Issues)
- พ.ร.บ. ควบคุมเครื่องดื่มแอลกอฮอล์ พ.ศ. 2551 และประกาศที่เกี่ยวข้อง
- การขายแอลกอฮอล์ผ่านแอปพลิเคชัน (Online Sale): ฟีเจอร์ "พรีออเดอร์เบียร์ 1 ลัง" เข้าข่ายการขายเครื่องดื่มแอลกอฮอล์ด้วยวิธีการทางอิเล็กทรอนิกส์ ซึ่งเป็นข้อห้ามตามกฎหมายอย่างชัดเจน
- การจัดโปรโมชันลดแลกแจกแถม: ฟีเจอร์ที่เกี่ยวข้องกับการสร้างโปรโมชันของร้านค้า (เช่น โปรเบียร์ 1 ลัง, Smart Upselling ยิงโปรเบียร์) ขัดต่อมาตรา 30 ที่ห้ามขายเครื่องดื่มแอลกอฮอล์โดยวิธีการลดราคา หรือเสนอสิทธิประโยชน์อื่นใด
- การโฆษณา (Advertisement): ฟีเจอร์แบนเนอร์โฆษณาแบรนด์เครื่องดื่ม หรือ Native Mini-Ads อาจเข้าข่ายการโฆษณาเครื่องดื่มแอลกอฮอล์ ซึ่งมีความเสี่ยงสูงมากตามมาตรา 32
- อายุของผู้ใช้งาน (Age Restriction)
- กลุ่มเป้าหมายหลักคือนักศึกษา (18-22 ปี) แต่กฎหมายห้ามจำหน่ายเครื่องดื่มแอลกอฮอล์แก่บุคคลอายุต่ำกว่า 20 ปีบริบูรณ์ การไม่มีระบบยืนยันตัวตนและการเข้าถึงแพลตฟอร์มของเยาวชน อาจทำให้บริษัทมีความผิดฐานสนับสนุนหรือเป็นตัวการร่วม
- พ.ร.บ. ระบบการชำระเงิน พ.ศ. 2560 (e-Payment)
